# Диагностическая проверка стола AutoPrinter

`E0BedChecker` — локальный кандидат для поиска детали на кадре стола. Он нужен для диагностической команды `recheck_bed`; результат не разрешает физический запуск и не завершает выполняемое задание. По умолчанию проверка выключена.

## Ограничение модели

Используется RF-DETR Small E0 из `printer-defect-server/models/releases/fdm-preprocessing-20261016/detection/E0/training_5epochs/checkpoint_best_total.pth`.

| Параметр | Значение |
|---|---|
| Версия | `fdm-detail-e0-20261016-8de7e8aa22e2` |
| Размер файла | `127479855` байт |
| SHA-256 | `8de7e8aa22e20893a563c0c04d28f0019dcad9ef8d805818df6fd2ec8b10866e` |
| Вход | исходный RGB кадр, `512×512` |
| Класс | `0` — деталь |
| Порог score | `0.5191324353218079` |
| NMS | `0.8` |
| Окружение inference | `rfdetr==1.11.0`, `torch==2.11.0`, `torchvision==0.26.0`, `Pillow==12.3.0` |

В тестовой выборке были 818 размеченных деталей: 806 обнаружены, 12 пропущены. Все кадры содержали детали; отрицательных кадров пустого стола нет. Поэтому обнаружение класса `0` возвращает `occupied`, а отсутствие обнаружений, ошибка модели или недостоверный кадр возвращают `unknown`. E0 никогда не возвращает `empty` и не квалифицирован для допуска к печати. Нельзя подменять эту модель классификатором спагетти, COCO-весами, другой версией или выбранным на тестовой выборке порогом.

## Настройка

Текущий этап не устанавливает зависимости, не скачивает и не копирует веса. Перед отдельным развёртыванием установите зависимости из таблицы в локальном окружении и разместите проверенный checkpoint по абсолютному пути. `bed_check_python` должен указывать на абсолютный путь к интерпретатору этого окружения.

В `[treed_autoprinter]` задайте:

| Параметр | Значение |
|---|---|
| `bed_check_enabled` | `true` для явного включения диагностической проверки; default `false` |
| `bed_check_model_path` | абсолютный путь к checkpoint с указанными размером и SHA-256 |
| `bed_check_python` | абсолютный путь к локальному Python с закреплёнными зависимостями |
| `bed_check_snapshot_url` | локальный адрес снимка; default `http://127.0.0.1:8080/?action=snapshot` |

`execution_enabled` остаётся отдельным параметром и по умолчанию выключен. `bed_check_enabled: true` не включает исполнение, а отсутствие или ошибка конфигурации закрывает проверку. Компонент создаёт checker без загрузки модели, открытия камеры и тяжёлых импортов; эти действия выполняются только при `recheck_bed`. Runner работает на CPU, запрещает сетевую загрузку модели и не сохраняет кадры.

Доставка Moonraker уже копирует все `*.py` из `moonraker/components`, а updater допускает `moonraker/treed_*.py`; оба пути включают `treed_autoprinter_bed.py` и `treed_autoprinter_bed_inference.py`. Отдельного шага установки модели нет.

Runner рассчитан на Linux: после проверки checkpoint он передаёт модели путь через `/proc/self/fd`. На Windows inference не поддержан и не проверялся. Этот этап не устанавливает веса и не запускал реальные веса; выполнение на целевом Moonraker runtime остаётся отдельной приёмкой.

Проверка получает новый кадр для каждого запроса, ограничивает размер ответа и принимает только JPEG. Запрос не использует cookies, credentials, redirects или proxy. Время получения ответа не доказывает свежесть сенсора: непустой `Age`, ошибка камеры и недостоверные данные дают `unknown`. Успешный inference также не доказывает, что физический стол пуст.

## Повторная проверка и статус

Авторизованный `POST /server/treed/autoprinter/control` принимает `{"type":"recheck_bed"}`. Действие доступно при подключённом компоненте и paired-состоянии даже при `execution_enabled: false`. `occupied` и `unknown` сохраняются в локальном durable-журнале; если задание находится в `verifying`, эти результаты его не завершают. Только квалифицированный провайдер может вернуть пригодное для завершения `empty`.

`GET /server/treed/autoprinter/status` показывает безопасную диагностику `bed_check` только при paired-состоянии. Снимок для backend сохраняет прежнюю форму, а `capabilities.bed_check` остаётся `false`. Endpoint не принимает доказательства или команды inference.

Backend по умолчанию не разрешает версии моделей: `allowed_model_versions` остаётся пустым, пока deployment отдельно не настроит allowlist. Для сопоставления этой версии потребуется `fdm-detail-e0-20261016-8de7e8aa22e2`; само добавление версии не меняет ограничение `live_qualified=false`.

## Граница допуска к печати

E0 не подтверждает пустой стол, поэтому не может разрешить начало печати или завершить задание. Установка весов, положительное обнаружение детали и успешный тест на кадрах с деталями не меняют этот запрет. Для квалификации потребуется отдельная выборка пустого стола, проверка ложных допусков и явное изменение контракта; эти действия отложены.

Адресные офлайн-проверки интеграции перечислены в [`tools/tests`](../tools/tests/README.md). Они используют подставные checker и runtime; реальные веса и устройство в них не участвуют.
