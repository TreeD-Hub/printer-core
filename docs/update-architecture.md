# Архитектура обновлений TreeD

Этот документ описывает существующую реализацию. Целевой контракт обновления без
ручных действий клиента, разрывы текущего пути и порядок перехода описаны в
[проекте автономного обновления](update-convergence.md).

## Что работает в этом срезе

Moonraker принимает запрос, но не владеет долгой операцией. Он передаёт проверенные аргументы fixed root-команде; systemd worker владеет последовательностью, блокировкой и итогом. Frontend может восстановить operation после перезагрузки страницы, Moonraker или UI-службы.

Для `printer-ui` worker скачивает точный release asset, сверяет SHA-256 с полем `digest` GitHub Release API, проверяет ZIP и manifest, публикует каталог, перезапускает `treed-shell.service` и требует три успешные локальные HTTP-проверки. До успешной проверки прежний UI остаётся в operation-specific каталоге отката. Ошибка публикации, readiness или остановка worker вызывает попытку восстановления; boot recovery возвращает старый каталог, когда он сохранён, либо подтверждает точный target manifest и HTTP readiness, если публикация уже завершилась.

Контрольная сумма GitHub защищает от повреждения или подмены при загрузке при доверии к GitHub API и TLS. Она не является отдельной подписью издателя. Политика независимой проверки подписи UI-пакета остаётся незавершённой.

## API и операция

`POST /server/treed/update/apply` принимает `requestId`, `targetId` и `targetTag`. `requestId` — UUID; старые клиенты без поля получают UUID от сервера. Успешный ответ быстро сообщает `accepted`, `operationId`, `status`, `phase`, `progress`, `message`, `targetId` и `targetTag`. Повтор того же `requestId` возвращает существующую операцию. Другой запрос не заменяет занятую очередь.

`GET /server/treed/update/status` читает локальное состояние и не делает сетевой refresh или firmware inventory. Старые поля ответа сохранены; добавлены `operation`, `latestOperation`, `history`, `status`, `phase`, `progress` и `resultCode`. `GET /check` параллельно проверяет релизы с таймаутом 7 секунд на источник. Проверка live MCU остаётся на `/firmware`.

Активные статусы: `queued`, `validating`, `downloading`, `installing`, `restarting`, `verifying`, `rolling_back`. Terminal статусы: `applied`, `rolled_back`, `error`, `rejected`. `progress` равен 0 в очереди, неизвестен (`null`) без измеримой метрики и равен 100 только после подтверждённой готовности UI.

Root-служба атомарно хранит текущую операцию и последние десять завершённых в `/var/lib/treed-update/state.json`; inter-process `flock` сериализует submit, worker и recovery. Файл синхронизируется на диск до замены, каталог — после неё. Systemd path-unit запускает worker при изменении состояния, закрывая промежуток между записью queued и запуском службы. `ExecStopPost` и boot recovery завершают состояние, если worker прервался.

## Обновление компонентов TreeD (`printer-core`)

`printer-core` теперь означает пакет `treed-core-runtime.zip`: наши конфиги,
Klipper host extensions, Moonraker components, camera scripts и команды
`treed-ui`, `treed-update-service`, `treed-update-apply`, `treed-core-update`.
Обычное обновление заменяет только runtime-файлы. Манифест новых выпусков также
содержит `provisioning.schema` и `provisioning.revision`: хеш shell-кода loader,
`runtime-versions.env` и манифеста моделей. Изменение этих требований,
отсутствие обязательных vision units или несовпадение закреплённых upstream SHA
переключает обновление на управляемый режим loader. Ошибки загрузки, контрольной
суммы и конфликты локальных файлов этот переход не разрешают.

Для миграции updater загружает `treed-mainshellos-source.zip` того же тега,
проверяет SHA-256 GitHub, безопасные пути ZIP, версию, зависимости, provisioning
revision и соответствие исходников runtime-пакету. Worker сохраняет блокировку
и журнал, устанавливает проверенные runtime-файлы и запускает
`loader/loader.sh` с `TREED_UPDATE_MANAGED_LOADER=1`.
Этот режим выполняет проверки, остановку служб, установку системных/runtime
зависимостей и служб, затем запуск и verify. Пересборка каталога конфигурации,
boot/CAN-настройки, сборка и прошивка MCU, установка нового UI исключены.
Калибровки `SAVE_CONFIG`, неизвестные файлы, overrides, credentials и локальный
журнал AutoPrinter сохраняются. Источником версии остаётся проверенный пакет;
baseline фиксирует updater после готовности устройства, а не loader из checkout.

До начала provisioning действует обычный runtime rollback. После начала loader
ошибка или прерывание записывается как ошибка provisioning: полный откат
системных пакетов не обещается. Worker сохраняет цель и планирует до трёх
автоматических повторов с задержками 30, 120 и 300 секунд. Отдельный короткий
systemd timer проверяет срок под неблокирующим общим lock; перезапуск ОС не
сбрасывает бюджет. Ошибки проверки пакета не превращаются в автоматический retry.
При исчерпании попыток остаются цель, диагностика и достоверный статус ошибки.

После сорванного provisioning обычная команда обновления может выбрать строго
более новый исправленный core-выпуск. Root проверяет прежний журнал и создаёт
связанную операцию; confirmed manifest остаётся прежним до успешной готовности.
Физическая база установки хранится отдельно. Запись новой цели продолжается
вперёд по проверенным подготовленным файлам, без отката отдельных файлов поверх
уже изменённых зависимостей. Снимки, история согласий и старый архив сохраняются.
Отказ загрузки, проверки пакета или старта службы до нового журнала не теряет
ссылку на эту базу: следующая команда может выбрать ещё более новый выпуск.
Существующий forward-only journal на стадии `validated`/`installing` продолжается
той же операцией; подробные границы приведены в
[контракте восстановления](update-convergence.md#восстановление-и-данные).

Порядок managed-шагов задан в `loader/managed-runtime.json`. Дополнительная
`managedRevision` охватывает этот план и его входные файлы, включая unit-файлы,
которые доставляет loader. Старая `provisioning.revision` сохраняет прежний
алгоритм: уже установленный updater может проверить новый source package и
запустить его loader без ручной подготовки. Ранний `update-recovery-bootstrap`
доставляет retry units до обновления зависимостей; старый процесс остаётся
владельцем операции до освобождения lock.

Исходники, before-images и журнал сохраняются для восстановления. Старые выпуски
без provisioning requirements остаются в прежнем runtime-контуре. Уже застрявший
старый updater, допускающий только повтор прежнего cached ZIP, не получает
исправленный код от одной публикации нового тега; этот случай отделён от
проверяемого перехода работающей старой установки в
[контракте автономного обновления](update-convergence.md#переход-с-уже-установленного-updater).

После проверки простоя worker временно показывает существующую тему TreeD
в Plymouth и возвращает ранее работавший интерфейс при завершении или ошибке.
Самостоятельный loader использует тот же помощник; управляемый loader оставляет
владение экраном внешнему worker. Экран показывает ожидание без выдуманных
процентов. Состояние владения хранится отдельно в `/run/treed-loading-screen`;
ошибка отображения не подменяет результат обновления и не вызывает остановку
Klipper или Moonraker. Если kiosk запускается в конце loader, он штатно
завершает Plymouth и принимает экран до окончательной проверки.

Release workflow публикует пакет после push в `treed-v2` (обычно merge PR)
или ручного запуска. Как в UI, версия сборки формируется автоматически:
`0.<run_number>.<run_attempt>`, тег core: `v0.<run_number>.<run_attempt>`.
Повышать `VERSION` в PR не требуется. Workflow записывает версию в свой checkout
и source asset; runtime и release manifests используют то же значение.
Ветка остаётся без автоматических коммитов. При push ручного тега `vX.Y.Z`
его версия должна совпадать с `VERSION` этого commit.
Тег и assets неизменяемы; совпадение существующего тега с
другим commit блокирует публикацию. Assets сначала загружаются в draft;
публикация выполняется после успешной загрузки полного набора. Повторный запуск
получает новую попытку и новый тег; опубликованный выпуск не перезаписывается.
Архив содержит schema/kind, версию, commit,
точные SHA совместимых Klipper/Moonraker и checksum каждого файла. Старый
source-only release не предлагает применимое обновление.

Worker вызывает `treed-core-update apply <tag> <operationId>` под общим lock.
Updater проверяет SHA-256 GitHub Release asset, ZIP, manifest, разрешённые
назначения и текущие upstream SHA/отсутствие tracked изменений.
Untracked-модули TreeD сверяются с ownership manifest и его хешами:
совпадающие управляемые файлы не считаются изменением upstream. Неизвестный
untracked-файл или правка tracked-файла блокирует обновление. Перед остановкой
служб требуются Klipper `ready` и отсутствие активной печати/паузы по `print_stats.state`.
Завершённое или отменённое задание и остаточные флаги макросов не блокируют update.
При активной паузе UI предлагает отменить печать и обновиться. Только после
подтверждения POST apply содержит `cancelPausedPrint: true`; Moonraker выполняет
`CANCEL_PRINT`, повторно проверяет состояние задания и затем передаёт запрос worker.
Без подтверждения активная пауза блокирует обновление; печатающее задание нельзя
отменить этим параметром.
После проверки пакета updater сам отправляет `TURN_OFF_HEATERS` и проверяет нулевые
heater targets перед остановкой служб; ждать остывания не требуется.
Установка заменяет отдельные управляемые файлы; неизвестные файлы не удаляются.
Удаление допускается только для файлов предыдущего ownership manifest.
Локальные правки управляемых файлов блокируют update; перенесите настройки в
штатные overrides. Занятое неизвестным файлом новое назначение также блокирует
установку. `SAVE_CONFIG` сохраняется целиком, включая последнее сохранение до
остановки Klipper. `local_overrides.cfg`, `treed_variables.cfg`,
`filament_motion_runtime.cfg`, `moonraker/generated`, снимки и пользовательские
данные не входят в package payload. Устройство сохраняет вычисленные loader
updater-секции Mainsail/Crowsnest, шаблоны рендерятся с его `PI_HOME`/`PI_USER`.

Штатное комментирование PID-строк в `printer.cfg` командой `SAVE_CONFIG` не считается
ручной правкой: updater сверяет исходные значения с записанным ownership hash.
Это работает и с manifest, созданным до калибровки одного или обоих нагревателей.
В новом `printer.cfg` заводские PID-поля, присутствующие в сохранённой калибровке,
остаются закомментированными, чтобы Klipper применял `SAVE_CONFIG`. Переносить
эти поля в `local_overrides.cfg` не нужно. Изменение значений исходных строк,
include-цепочки и остальных управляемых файлов по-прежнему блокирует обновление.

`POST /server/treed/settings/reset` с JSON `{"confirm": true}` сбрасывает только
`local_overrides.cfg` по пути `local_overrides_path` из `[treed_update]`.
Перед атомарной заменой пустым файлом сохраняется копия рядом:
`local_overrides.cfg.<uuid>.bak`. Ошибка создания копии отменяет сброс.
Значения возвращаются к установленному профилю; `SAVE_CONFIG`, `treed_variables.cfg`
и настройки датчика филамента сохраняются. Endpoint запрещён при активной печати,
паузе, неизвестном состоянии задания и выполняющемся обновлении. После сброса
выключается нагрев и запрашивается `RESTART`; `restartRequired: true` в ответе
означает, что файл уже сброшен, но перезапуск нужно выполнить вручную.

До первой замены сохраняются fsync before-images и journal в
`/var/lib/treed-update/core/<operationId>`. Записи отдельных файлов атомарны;
многофайловая установка защищена остановкой Klipper/Moonraker и recovery.
Сбой установки/readiness возвращает прежние файлы, права и ownership manifest.
Три последовательных проверки Klipper `ready` и обязательных Moonraker
components подтверждают результат. Только затем обновляется
`/var/lib/treed-update/core-manifest.json`. Worker/boot recovery откатывает
незавершённый journal; committed результат подтверждается readiness. Ошибка
возврата или readiness не называется успешным rollback. Резервные файлы остаются
для диагностики; текущий updater автоматически их не удаляет.

На чистой системе команды и baseline доставляет обычный loader. В установленной
системе с поддержкой source provisioning их доставляет само обновление. После успешного
`verify` записывается baseline после сверки реально доставленных файлов с
исходниками выпуска и SHA текущих зависимостей. При
`TREED_ALLOW_HARDWARE_NOT_READY=1` baseline не записывается. Виджет разрешает core
update только после установки команды и baseline. Текущая версия читается из
runtime manifest; standalone Git checkout определяет релиз по semver-тегу
именно своего коммита, а при отсутствии такого тега использует `VERSION`.
Standalone `apply` держит общую блокировку весь запуск; baseline и завершение
операции используют проверенный унаследованный дескриптор, не снимая lock владельца.
GitHub digest/TLS используется с той же моделью доверия, что у UI; отдельной
подписи издателя runtime-пакета пока нет. Readiness не заменяет испытания
движения, нагрева и калибровки при выпуске изменённых макросов.

## Системное A/B обновление: пока недоступно

Системный A/B updater остаётся отдельным будущим контуром. Этот репозиторий не
содержит подтверждённой разметки устройства, интеграции загрузчика, production
RAUC system bundle, ключа подписи, миграции постоянных данных или обязательной
post-boot health-проверки.

`treed-ab` сейчас только сообщает fail-closed состояние. Установка RAUC или наличие platform attestation сами по себе не разблокируют кнопку. Для включения требуются все следующие части:

1. Зафиксировать модели плат, загрузчик, схему разделов, объём накопителя и способ восстановления.
2. Собрать неизменяемый системный bundle со всеми компонентами, compatibility manifest и подписью; проверять подпись до записи.
3. Реализовать запись только неактивного слота и ограниченные попытки загрузки; исходный подтверждённый слот сохранять.
4. Разделить системные файлы и пользовательские данные, подготовить миграцию настроек с возможностью возврата.
5. Проверить на целевой плате загрузку, службы, обязательные MCU, интерфейс и стабильность; подтверждать новый слот лишь после health gate.
6. Испытать потерю питания на каждой границе, ошибку записи, повреждённый пакет, отказ платы, rollback и восстановление через сервисный носитель.
7. Только после этого разрешать отдельные системные выпуски; capability пакета компонентов TreeD не подтверждает готовность A/B.

Обновление прошивки MCU остаётся отдельной операцией: возврат OS-слота не откатывает прошивку контроллера. Выпуск системы должен явно объявлять совместимость с установленными версиями MCU.

## Проверки

`tools/tests/test_treed_update_component.py` проверяет совместимость POST,
локальный status, runtime capability и версию. `tools/tests/test_treed_update_service.py`
проверяет очередь и передачу core операции, прерывание и recovery UI.
`tools/tests/test_treed_core_update.py` проверяет реальный package build,
сохранность локальных данных, rollback и прерывание многофайловой установки.
Эти проверки не заменяют испытания systemd и принтера на целевой плате.
