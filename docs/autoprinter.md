# AutoPrinter на стороне принтера

Компонент хранит очередь на принтере и синхронизирует её с backend. Локальный журнал также сохраняет состояния исполнения и события, которые backend ещё не подтвердил.

Проверка пустых кадров, дообучение E0, состояние «стол чист» и алгоритм автосъёма
зафиксированы в [TODO AutoPrinter](autoprinter-todo.md).

## Включение

Секция `[treed_autoprinter]` включает очередь, локальное исполнение и проверку стола без фича-флагов. Параметры `enabled`, `execution_enabled` и `bed_check_enabled` больше не используются. Для связи задайте `printer_id`, `profile_id`, `api_origin`, `credentials_path` и `storage_path`. Origin должен быть HTTPS без пути, query и fragment. Credential-файл содержит ровно `printer_id` и `secret` в JSON; в POSIX-системе файл должен быть доступен только владельцу. Не сохраняйте credential в репозитории, Moonraker-конфиге или журнале.

Для анализа стола нужна локальная служба `treed-vision` с проверенными весами и закреплённым окружением. Настройка и ограничения кандидата E0 описаны в [проверке стола](autoprinter-bed-check.md). E0 возвращает только `occupied` или `unknown`; он не может разрешить запуск или завершить задание.

Без корректной конфигурации компонент остаётся загруженным и сообщает `configured: false`. Он не создаёт API для чтения локальных файлов.

## Аккаунт и привязка

Авторизованный `POST /server/treed/autoprinter/pairing` возвращает `code`, `expires_at` и `verification_url`. При открытии «Аккаунта» UI один раз запрашивает код для непривязанного принтера, если сохранённого кода нет. После ошибки или отмены в открытом экране повторный запрос выполняется только по нажатию «Получить код». Core отправляет backend заголовок `X-TreeD-Pairing: persistent-v1`: такой код не имеет срока действия (`expires_at: null`) и действует до привязки или отмены. Core сохраняет его в локальной SQLite; повторный запрос и перезапуск возвращают тот же код без перевыпуска. `GET /server/treed/autoprinter/status` возвращает его в `pairing`, пока устройство не привязано.

Авторизованный `POST /server/treed/autoprinter/pairing/cancel` отменяет код через device API backend. Core очищает локальный код только после подтверждения `cancelled: true`; при ошибке отмены код сохраняется. Поддержка отмены обозначается `capabilities.pairing_cancel`. Привязка и смена состояния устройства также очищают локальный код. Backend хранит только хеш и отклоняет повторное использование погашенного кода.

QR в настройках «Аккаунт» открывает ссылку; ручной ввод кода ведёт к тому же подтверждению на сайте. Открытие ссылки и вход сами по себе не привязывают устройство. Для старых клиентов без заголовка backend сохраняет конечный срок из конфигурации (по умолчанию пять минут). Новый UI и Core также принимают конечный `expires_at` от старого backend.

Backend формирует ссылку из `FRONTEND_URL`. Core проверяет её origin, путь `/autoprinter/connect` и фрагмент с выданным кодом. Если сайт и API находятся на разных origin, задайте `frontend_origin` в `[treed_autoprinter]`; без него ожидается `api_origin`. Оба origin в конфигурации core должны использовать HTTPS без пути, query и fragment. Не подставляйте адрес страницы подключения вместо origin.

После синхронизации `GET /server/treed/autoprinter/status` показывает имя устройства в `display_name`, ограниченный профиль владельца в `owner_profile` и поддержку сценария в `capabilities.account_linking`. Профиль содержит `display_name` и необязательный `avatar_url` (HTTPS, до 2048 символов, без логина и пароля в URL; `null`, если аватара нет). Пароль, email и пользовательская сессия на принтер не передаются. При отзыве доступа и завершённой отвязке профиль скрывается. UI загружает изображение напрямую без Referer; если загрузка не удалась, показывает инициалы.

Core отправляет заголовок `X-TreeD-Owner-Profile: avatar-v1` в запросах к device API. Backend добавляет `avatar_url` только при этом заголовке: прежний Core продолжает получать профиль с одним `display_name`, прежний backend игнорирует заголовок. Данные берутся из существующей проекции владельца с ограниченным сроком действия, без доступа device runtime к основной базе пользователей. Перед запуском обновлённого backend нужна миграция `2026_10_20_000001_add_owner_avatar_to_autoprinter_grants` в базе AutoPrinter; сама правка исходников миграцию не выполняет.

Авторизованный `POST /server/treed/autoprinter/account/unlink` сохраняет намерение отвязки для текущего `binding_epoch` и сразу блокирует новые запуски. `unlink_pending` остаётся видимым при потере сети и после перезапуска. Продолжение очереди не снимает этот запрет. Запрос из кабинета приводит к тому же ожиданию после следующей синхронизации.

Финальная отвязка требует ответа backend и свежего наблюдения покоя через адаптер Moonraker: принтер готов, фаза `idle`, печать и обслуживание не активны, очередь безопасна. Текущая печать и завершающие операции продолжаются; отвязка не отправляет отмену, старт или повторный автосъём. Неизвестное состояние и пауза не считаются покоем. Данные и история прежней привязки сохраняются в её namespace и не передаются новому владельцу.

## Диагностика и бюджет журнала

Локальный status дополнительно возвращает `protocol_version: 1`,
`configuration_version: 1` и `last_sync_at` — UTC-время последнего успешно
обработанного sync в текущем процессе. Ошибка запроса или обработки ответа
не обновляет время; после перезапуска оно равно `null` до успешной связи.
Для unpaired/revoked-состояния время скрыто. Эти поля не добавляются в wire
snapshot для backend.

При `binding_state: "paired"` локальный status также возвращает `queue` — до
1000 заданий по возрастанию `position`, `queue_total` — полный размер текущей
очереди, и `queue_truncated` — признак, что показан не весь список. Элемент
содержит только `run_id`, `position`, `state`, `series_id` и `copies_per_run`;
если состояние исполнения ещё не записано, используется `queued`. Для старой
записи отсутствующие `series_id` или `copies_per_run` равны `null`;
unpaired/revoked-состояния очередь пуста, `queue_total` равен нулю,
`queue_truncated` — `false`.
`capabilities.queue` и `capabilities.pairing` показывают поддержку локального
списка и связывания. `capabilities.bed_check_diagnostic` показывает наличие
провайдера диагностики; `capabilities.bed_check` по-прежнему означает
квалифицированную live-проверку.

При paired-состоянии `journal` показывает `allocated_bytes`, `limit_bytes`
и `at_capacity`. Бюджет задаётся `max_journal_bytes` в `[treed_autoprinter]`,
по умолчанию 67108864 байт (64 МиБ). SQLite округляет бюджет вниз до размера
страницы. Лимит относится к основному файлу БД; rollback journal во время
транзакции и G-code учитываются отдельно, поэтому свободное место также нужно.
Предел реализован через SQLite [`max_page_count`](https://www.sqlite.org/pragma.html#pragma_max_page_count).
`at_capacity` означает отсутствие места для новых страниц, а не запрет любой
записи: SQLite ещё может использовать свободные страницы.

История, dedup команд и неподтверждённые события автоматически не удаляются.
Запись, требующая роста сверх лимита, завершается ошибкой SQLite и откатывается;
операции AutoPrinter могут блокироваться. Штатные остановка и отмена Moonraker
не зависят от этой БД. Перед расширением бюджета сохраните весь каталог
AutoPrinter при остановленном компоненте; не удаляйте `store.sqlite3` ради
продолжения очереди. Если существующая БД уже больше нового лимита, компонент
остаётся unconfigured с `journal_limit_exceeded`, не обрезая файл.

## Доставка и совместимость

Loader копирует компоненты и проверяет их загрузку через `/server/info`.
Runtime updater проверяет комплект из семи модулей `treed_autoprinter*.py`
и общего клиента `treed_vision_client.py`;
частичный комплект отклоняется до установки. После установки, при recovery
и rollback он проверяет компоненты, требуемые соответствующим manifest, включая
`treed_autoprinter`, если тот входит в выпуск. Запись в `failed_components`
не считается успешной загрузкой. Переход со старого runtime без AutoPrinter
сохраняется: до установки от него не требуют нового компонента.

Credentials, `storage_path` с привязкой и журналом, G-code аккаунтов и внешние
веса не входят в payload runtime updater. Обновление и rollback их не удаляют.
Общий vision runtime, camera adapter и клиент доставляются одним комплектом.
Первую установку systemd-службы выполняет loader. Он принимает локальные
артефакты моделей, проверяет размер и SHA-256 и меняет их только между заданиями.
ML-зависимости изолированы от Moonraker: loader использует проверенное окружение
`TREED_VISION_PYTHON` либо локальный `TREED_VISION_WHEELHOUSE` с закреплёнными версиями.
Настройки доставки описаны в [README службы](../runtime-scripts/treed-vision/README.md).
Отсутствие runtime или весов означает `unavailable`; удалённого анализа по умолчанию нет.

## Синхронизация

Компонент отправляет ограниченные снимки состояния, события и сохранённые результаты команд. Очередь и журнал остаются на принтере; backend подтверждает только переданные события и результаты. При `control_epoch_mismatch` компонент применяет новое состояние binding, затем синхронизируется снова без подтверждения результатов или событий старого поколения. Ответ HTTP 409 блокирует исполнение и требует ручного восстановления протокола.

Локальный executor опрашивает очередь примерно раз в секунду независимо от сетевого sync и его backoff. Оба контура используют один lock. Медленный sync-запрос задержит следующий executor tick, status и локальные действия до завершения запроса.

Скачанный asset проверяется по размеру и SHA-256 и сохраняется в `storage_path`. Backend получает receipt только после успешной durable-записи. Если ответ на receipt потерялся и backend перестал рекламировать передачу, компонент повторно отправляет локальную запись из `pending_receipts`. Новая привязка использует отдельный namespace; данные прежней привязки сохраняются на диске, но не входят в текущую очередь.

Если локальный журнал очереди и серверная ревизия не позволяют доказать, что очередь восстановлена, компонент блокирует дальнейший sync и показывает `queue_recovery_required`. На этом этапе нет команды автоматического сброса или восстановления: сначала сохраните локальный каталог AutoPrinter и сверьте его с backend вручную. Компонент не принимает новую пустую очередь как замену потерянной.

## Автономный пакет

Состояние реализации, выполненные проверки и аппаратные ограничения:
[приёмка локального зрения](local-vision-acceptance.md).

Пакет объединяет существующие assets, серии и запуски в одном неизменяемом манифесте. Отдельной очереди и второго механизма передачи файлов нет. Backend принимает `POST /api/autoprinter/printers/{printer}/packages` с `Idempotency-Key` и телом:

```json
{
  "package_id": "dc34b31e-95c5-4d65-9fbb-cfc6175e6092",
  "groups": [{
    "asset_id": "824be043-126e-443f-ab96-10e853d24e37",
    "repeat_count": 2,
    "copies_per_run": 1,
    "completion_profile_id": "treed_v2_corexy_v1"
  }]
}
```

Идентификатор профиля завершения нужно брать из доступных профилей backend; пример показывает форму запроса. API проверяет владельца принтера, текущую привязку и подтверждённую capability `offline_packages_v1`. Все assets должны быть `stored` у этого принтера. Backend резервирует серии и запуски вместе с одной командой `enqueue_package` в одной транзакции. Ответ `202` со `state=pending` означает ожидание подтверждения принтером.

Манифест содержит `package_id`, `version`, `printer_id`, `binding_epoch`, `profile_id`, `policy_version` и упорядоченный список `runs`. Каждая группа фиксирует `series_id`, `asset_id`, размер, SHA-256, `copies_per_run`, профиль завершения и упорядоченные `run_ids`. `manifest_hash` вычисляется по UTF-8 JSON с отсортированными ключами объектов, без пробелов и экранирования Unicode; числа с плавающей точкой не допускаются. Порядок элементов массивов сохраняется.

Принтер повторно проверяет все файлы по размеру и SHA-256. Запись пакета и добавление всех запусков атомарны: отсутствующий или повреждённый файл не оставляет частично принятую очередь. Приём пакета не включает исполнение и не обходит live-проверку стола.

Принятый пакет сохраняет локальное разрешение при потере сети, истечении срока команды доставки и потере подтверждения. Backend не освобождает резервирование по таймауту; повторная доставка не добавляет вторую копию запусков. Старое состояние backend не должно заменять уже записанные локальные переходы. Изменение `binding_epoch` изолирует старую очередь и журнал от нового владельца.

Обычная команда `reorder_queue` не меняет принятый пакет. Для изменения состава или порядка требуется новая согласованная версия; предыдущая версия должна завершиться или быть отменена. Локальный status возвращает `active_package` с версией, хешем, состоянием и количеством оставшихся запусков.

После перезапуска выполнение блокируется до решения оператора и свежей проверки безопасного покоя. Локальный `resume_queue` может разрешить дальнейшее исполнение принятого пакета без backend. Эта возможность не распространяется на старые отдельные серии и не снимает блокировку неизвестного исхода `start_intent`. Неподтверждённые события сохраняются; при заполнении журнала новые запуски блокируются, события ради продолжения не удаляются.

## Локальное управление

Авторизованный `POST /server/treed/autoprinter/control` принимает `pause_queue`, `resume_queue`, `stop_after_current`, `recheck_bed`, `pause_current_print`, `cancel_current_print` и `cancel_package`. Первые четыре действия принимают только поле `type`. Для паузы или отмены текущей печати передайте также UUID `run_id` и UUID `action_id`; компонент сверяет задание с текущим запуском. Для отмены остатка пакета передайте `package_id` и `action_id`: текущая печать и записи со `start_intent` не отменяются. Повтор одного `action_id` возвращает сохранённый результат. Endpoint не принимает команды запуска, пути файлов или доказательства проверки стола.

После подтверждённого AI-дефекта обычный `RESUME` продолжает только текущую печать. Блокировка серии сохраняется в журнале. Локальный `resume_queue` снимает её после свежего наблюдения безопасного покоя и проверки отсутствия незавершённого физического намерения. Ошибка записи блокировки также закрывает следующий запуск; временное освобождение места само по себе не разрешает продолжение. UI показывает причины через `hold` и `recovery_required`.

Локальный `stop_after_current` сохраняет запрет следующего запуска в durable
`local_pause`. Текущая печать продолжает reconcile и завершение; остановка не
вызывает `device.pause`. Remote `resume_queue` снимает только remote pause и не
сбрасывает этот запрет. После завершения текущего задания и перезапуска очередь
остаётся закрытой до явного локального `resume_queue`.

Remote `reorder_queue` должен перечислять точный набор запусков в состоянии
`queued` без `start_intent`. Переставляются только их текущие позиции; активные,
неопределённые и завершённые записи остаются на месте.

При корректной конфигурации компонент создаёт адаптер принтера и executor без дополнительных переключателей. Если адаптер недоступен, исполнение остаётся выключенным. Поля `enabled` и `execution_enabled` в status сообщают состояние компонента и доступность исполнения. В текущем runtime нет квалифицированного провайдера проверки стола, поэтому физический запуск остаётся заблокированным. Проверка модели или тестовый provider не заменяют live-квалификацию и аппаратную приёмку снятия деталей.

Ответ `POST /server/treed/autoprinter/control` сохраняет текущие поля status и
добавляет `action_result` с `type`, `command_id`, `state` и `result`. Для
локальных действий `command_id` равен `null`; состояния результата —
`executed`, `rejected` или `uncertain`. Для паузы и отмены печати возвращается
исходный durable-результат команды с её UUID, включая результат повторного
`action_id`. `recheck_bed` со статусом `executed` означает, что проверка
завершилась: `occupied` и `unknown` не подтверждают пустой стол и не разрешают
печать. При недоступном доказательстве результат имеет состояние `rejected`
и код `bed_proof_unavailable`.

Файлы, подготовленные для печати, хранятся отдельно от очереди assets. Spool ограничен 1 ГиБ и сохраняет резерв 16 МиБ свободного места; при исчерпании места новые задания блокируются. Автоматического удаления spool-файлов нет. Оператор управляет свободным местом штатными средствами Moonraker.

Если компонент не может определить, началась ли печать после start intent или перезапуска, он блокирует очередь и не повторяет старт. Не запускайте это задание повторно, пока оператор вручную не сверит состояние принтера и историю; в текущем компоненте нет endpoint для снятия такой блокировки.

## Границы исполнения

- Компонент не принимает удалённую команду автоматического старта и не добавляет задания в очередь Moonraker.
- Адаптер проверяет состояние `job_queue`, принтера и обслуживания, копирует проверенный G-code без изменений и вызывает только штатный Klippy API старта, паузы или отмены.
- Запуск требует свежего live-доказательства пустого стола. В production провайдер такого доказательства пока не подключён; модель и физическая готовность не подтверждены.
- Проверка E0 является диагностической: `capabilities.bed_check` остаётся `false`, а проверка пустого стола не становится доступной для запуска или завершения.
- Адаптер не изолирует привилегированную консоль и все возможные пути ручного старта печати.
- Нет endpoint для чтения, перечисления или загрузки сохранённых файлов. Файл задания не появляется в каталоге G-code до подготовки конкретного запуска.
- Отзыв credential обнаруживается только при следующей успешной попытке связи; офлайн-принтер не может узнать об отзыве немедленно.

Адресная проверка без сети и устройства: `python -B tools/tests/test_treed_autoprinter_component.py`. Loader доставляет локальное хранилище, компонент и транспорт, затем требует успешной загрузки компонента, даже когда feature выключен.
