# Project Audit Checklist: treed-mainshellOS

## 1) Базовый контракт аудита

- Работать в режиме read-only: не редактировать файлы, не менять git-историю.
- Формат вывода findings: сначала `P0`, затем `P1`, затем `P2`.
- На каждый finding фиксировать:
  - Факт
  - Риск
  - Действие
  - Доказательство (`path:line`)

## 2) Язык и стиль ответа

- Рабочий язык аудита: русский.
- Формулировать выводы коротко и технически точно, без воды.

## 3) Loader и runtime-логика

Проверять в `loader/**` и связанных шагах:

- Идемпотентность шагов provisioning.
- Явную fail-fast логику для критичных сервисов (`klipper`, `moonraker`).
- Явный best-effort только для опциональных сервисов (`KlipperScreen`, `crowsnest`).
- Отсутствие silent skip в обязательных шагах.
- Документирование новых переменных окружения в `loader/steps/README.md` или профильной документации.

## 4) Klipper/Moonraker конфиги

Проверять в `klipper/**` и `moonraker/**`:

- Валидность include-цепочки.
- Отсутствие конфликтов ownership/source-of-truth.
- Для `klipper/profiles/rn12_corexy_v1`:
  - Модульность (один файл = одна зона ответственности).
  - Отсутствие необоснованного разнесения одной сущности по разным файлам.
  - Сохранение runtime override-механизмов как локальных.

При затрагивании `klipper/**` запускать:

```bash
python tools/validate_klipper_configs.py
```

## 5) Формат комментариев в коде

Для `loader/**`, `runtime-scripts/**`, `moonraker/**`, `plymouth/**`, `tools/**` проверять:

- Наличие заголовка файла с назначением и контуром (required/best-effort/read-only, если применимо).
- Разметку логики блоками вида `# Блок N: ...`.
- Комментарии должны объяснять цель и контракт блока, а не повторять синтаксис.

## 6) Документация и структура каталогов

Проверять, что:

- Документация соответствует фактическому коду, а не планируемому поведению.
- Обновляются только затронутые документы.
- Для затронутых каталогов есть `README.md` с назначением и правилами использования.

## 7) Проверочные ожидания для изменений

Если аудитируется набор правок, дополнительно проверять наличие/результат базовых проверок:

- Для shell-скриптов: синтакс-проверка `bash -n` (или явная фиксация ограничения среды).
- Для loader-изменений: идемпотентность, fail-fast/best-effort, отсутствие silent skip.
- Для Klipper/Moonraker: валидность include-цепочки и отсутствие конфликтов ownership.
- Если часть проверок не выполнена локально, это должно быть явно отмечено.

## 8) Ограничения среды

Учитывать ограничения локальной среды Windows 11 + PowerShell:

- Linux-утилиты и `bash -n` могут быть недоступны без WSL.
- Если проверка не выполнена локально, явно фиксировать это в отчете.
- Рекомендовать запуск на Raspberry Pi/в CI для Linux-специфичных проверок.

## 9) Git-дисциплина в рамках аудита

Во время аудита не выполнять:

- `push`, merge в `main`, удаление веток.
- `amend`, `rebase`, `reset --hard` и другие потенциально разрушительные операции.
- Откат чужих изменений без явного запроса.

## 10) Критерий завершения аудита

Аудит завершен, когда:

- Проверено ровно то, что запросил пользователь.
- Findings отсортированы по `P0 -> P1 -> P2` и имеют доказательства `path:line`.
- Явно указаны ограничения проверки и непокрытые зоны.
