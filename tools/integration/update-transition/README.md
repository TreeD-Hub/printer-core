# Проверка перехода обновления

Сценарий готовит старое состояние Core v0.49.2, запускает обновление через API
Moonraker, прерывает настоящий `dpkg --unpack` и ожидает автоматического
восстановления. После него запускается следующее обновление и проверяется
сохранность данных. **Полный прогон этого сценария пока не подтверждён**; сам
факт наличия файлов не означает готовности выпуска.

Перед объявлением апдейта готовым агент обязан выполнить этот сценарий локально
в изолированной VM и сохранить SHA, хеши пакетов и журналы результата.
Автоматические `contracts` и `release` его не запускают. Для отдельного ручного
прогона в GitHub Actions сохранён `update-transition.yml` с `workflow_dispatch`.

Проверку предполагается выполнять только в отдельной одноразовой Linux VM с
настоящим systemd и без доступа к устройствам принтера. В испытании использован
Debian 12 genericcloud в QEMU; этот контур не подтверждает работу CAN, MCU,
нагрева, движения или калибровки на оборудовании.

- `klippy-fixture.py` реализует используемую часть Unix-протокола Klippy и
  состояние admission gate. Moonraker остаётся настоящим. Сам макрос gate и
  его работа с физическим принтером этим имитатором не проверяются.
- `sitecustomize.py` подставляет локальные данные только для фиксированных URL
  GitHub release `TreeD-Hub/printer-core`. Он читает `/opt/treed-fixture/releases/<tag>/release.json`
  и два архива рядом с ним. Проверки URL, SHA-256 и updater envelope выполняет
  настоящий updater. Файл подключается через `PYTHONPATH` только к тестовой
  systemd-службе и не предназначен для установки на принтер.

Также используются отдельная имитация CAN-службы и ответов `ip` для `can0`.
Обновление и строгий `verify` выполняются без diagnostic override; корневая
проверка состояния печати, gate и остановки служб не заменяется имитатором.
Экранный UI в fixture отсутствует: сценарий проверяет, что managed Core
обновляется при недоступном старом UI. Сам UI этот сценарий не проверяет.
В старом состоянии присутствуют настоящие закреплённые исходники Crowsnest;
служба камеры и физическая камера не запускаются. Перед запросом обновления
Moonraker перезапускается с конфигом на диске и проходит проверку готовности.

## Запуск

Нужны Python 3.11+, работающий Linux Docker Engine, доступ к интернету, не менее
24 ГиБ свободного места для гостевого диска и дополнительное место для образов
и журналов. QEMU работает без privileged-контейнера и без `/dev/kvm`. Требуются
архивы runtime и source для двух последовательно возрастающих тестовых выпусков.
Рабочий каталог должен быть новым: в нём останутся гостевой диск и журналы.

```powershell
python tools/integration/update-transition/launch.py `
  --work-dir D:\Dev\_scratch\printer-core\transition-run `
  --first-runtime <первый-runtime.zip> --first-source <первый-source.zip> `
  --next-runtime <следующий-runtime.zip> --next-source <следующий-source.zip>
```

Замените все пути в угловых скобках на реальные пути к архивам. Launcher
проверяет SHA-256 закреплённого Debian genericcloud build `20261026-2643` и
архивов опубликованного v0.49.2, затем создаёт VM с 2 vCPU, 4 ГиБ памяти и
24-ГиБ диском. Для двух переданных выпусков fixture выдаёт локальные release
metadata; настоящий updater проверяет архив и сохранённый updater. Результат и
логи сохраняются в указанном каталоге. При ошибке команда возвращает ненулевой
код. Успешный прогон на VM не заменяет проверку оборудования.
