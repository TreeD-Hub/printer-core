# AGENTS.md — рабочий стандарт для `treed-mainshellOS`

## 1) Назначение

Этот файл задает постоянные правила работы агента в репозитории:
- как выполнять задачи;
- как оформлять изменения;
- как проводить аудит;
- когда можно делать commit/push.

Если запрос пользователя конфликтует с этим файлом, приоритет у явного запроса пользователя, кроме случаев небезопасных или разрушительных действий.

## 2) Язык и стиль

- Рабочий язык: русский.
- Комментарии в коде: русский, лаконично, только по делу.
- Сообщения коммитов: русский.
- Описание коммита (body): русский, с кратким объяснением что/зачем/как проверено.
- Коммуникация: коротко и технически точно, без воды.

## 2.1) Формат сообщения коммита

- Заголовок коммита: короткий, предметный, в одну строку.
- Описание коммита (body): структурированное, с реальными переносами строк и списками.
- Не использовать буквальные символы `\n` в тексте коммита.
- Рекомендуемый шаблон body:

  Что:
  - пункт 1
  - пункт 2

  Зачем:
  - причина 1
  - причина 2

  Проверка:
  - команда/проверка 1
  - команда/проверка 2

## 2.2) Локальная среда агента

- Базовая локальная среда: Windows 11, shell: PowerShell.
- При локальном выполнении учитывать различия синтаксиса (`;` вместо `&&`, экранирование, кавычки, пути).
- Linux-утилиты и shell-проверки (`bash`, `sed`, `awk`, `chmod`, `find -print0`, `xargs -0`) считать локально недоступными без установленного WSL-дистрибутива.
- Если Linux-команда не исполнима локально, выполнять проверку/запуск на целевой Linux-системе (Raspberry Pi) или в CI.
- Для shell-скриптов в репозитории сохранять Unix-окончания строк (LF); при ручном запуске на Pi при необходимости нормализовать CRLF.
- При правках `AGENTS.md` обязательно сохранять UTF-8 без потери кириллицы; перед ответом проверять `git diff AGENTS.md` и убеждаться, что текст читается корректно (без «кракозябр»).

## 2.3) Формат комментариев в коде (зафиксированный стиль)

- Для `loader/**`, `runtime-scripts/**`, `moonraker/**`, `plymouth/**`, `tools/**` использовать единый структурный формат комментариев.
- В начале файла добавлять заголовок с назначением и контуром (required/best-effort/read-only, если применимо), например:

  ```text
  # ==========================================
  # <ТИП/СЛОЙ>: <ИМЯ>
  # ==========================================
  # Назначение:
  # - ...
  # Контур:
  # - ...
  ```

- Внутри файла размечать логику блоками вида `# Блок N: <смысловой этап>`.
- Комментарии должны объяснять цель и контракт блока (почему/когда), а не пересказывать синтаксис строки.
- Для оркестраторов (например `loader.sh`) у шагов в списках добавлять короткое описание назначения прямо на строке шага.
- При задаче «причесывание комментариев» не менять поведение кода: только комментарии/документация/пустые строки.

## 3) Ветки и Git-дисциплина

- Основная рабочая ветка: `dev`, если пользователь не указал другую.
- В `main` ничего не сливать и не пушить без прямого явного указания пользователя.
- `push` выполнять только после явного разрешения пользователя (`"коммить и пуш"`, `"пуш"` и т.п.).
- Не делать `amend`, `rebase`, `reset --hard`, удаление веток и другие потенциально опасные git-операции без явного запроса.
- Не откатывать чужие изменения без прямого указания.

## 4) Формат выполнения задач

### 4.1 Если запрос = аудит

- Режим read-only: без правок файлов.
- Выводить findings с приоритетом `P0 -> P1 -> P2`.
- Для каждого finding фиксировать:
  - факт;
  - риск;
  - действие;
  - доказательство (путь/строка).

### 4.2 Если запрос = правки

- Менять только то, что нужно для задачи, без лишнего рефакторинга.
- Сначала выполнить правки, затем проверить логику/структуру/синтаксис.
- Перед коммитом показать краткий результат проверки.

## 5) Минимальные проверки перед commit

- Для измененных shell-скриптов: синтакс-проверка (`bash -n`).
- Если локальная среда агента = Windows без установленного WSL-дистрибутива, `bash -n` локально не запускать повторно в каждом таске:
  - один раз явно фиксировать ограничение проверки;
  - по возможности выполнять синтакс-проверку на целевой Linux-системе (Pi) или в CI;
  - не считать это блокером, если задача не требует немедленного локального bash-run.
- Для изменений в loader:
  - проверка идемпотентности шага;
  - проверка fail-fast/best-effort логики;
  - отсутствие silent skip для критичных сценариев.
- Для изменений в конфигах Klipper/Moonraker:
  - валидность include-цепочки;
  - отсутствие конфликтов ownership/source-of-truth.
- Если часть проверок невозможно выполнить локально, явно это указать.

- Для правок в `klipper/**` в конце задачи запускать `python tools/validate_klipper_configs.py` (локально или в CI) и фиксировать результат.

## 6) Правила для loader/steps

- Критичные сервисы (`klipper`, `moonraker`) — строгий контур ошибок (не маскировать сбои).
- Опциональные сервисы (`KlipperScreen`, `crowsnest`) — допускается best-effort, если это не ломает базовый provisioning.
- Избегать неявного поведения: если шаг обязателен, он не должен тихо пропускаться.
- Новые переменные окружения документировать в `loader/steps/README.md` и/или профильной документации.

## 7) Правила для профиля Klipper (`klipper/profiles/rn12_corexy_v1`)

- Поддерживать модульную структуру: один файл = одна зона ответственности.
- Не разносить одну сущность по разным файлам без явной причины.
- Макросы и комментарии держать в понятном и поддерживаемом виде.
- Локальные override-механизмы не ломать (runtime overrides должны оставаться локальными).

## 8) Документация

- Обновлять документацию только если она затронута текущей задачей или явно запрошена.
- Не переписывать docs «по пути» без необходимости.
- При правках docs сохранять соответствие фактическому коду/пайплайну.
- В каждой каталоговой директории репозитория должен быть `README.md` с кратким назначением и правилами использования.

## 8.1) Формат README (зафиксированный стиль)

- README должен отражать фактический код в директории, а не «планируемое» поведение.
- Базовая структура README:
  - что это за слой/каталог;
  - состав файлов или подсистем;
  - контракт/инварианты;
  - деплой/runtime-пути (если есть);
  - команды запуска/проверки (если применимо);
  - связанные документы/соседние слои.
- Для каталогов-оркестраторов использовать явный реестр шагов/сценариев с типом (`required`/`optional`) и назначением.
- При удалении или переносе документа сначала обновлять все ссылки на него в репозитории.

## 9) Запрещено без явного запроса

- Пушить в удаленный репозиторий.
- Сливать в `main`.
- Удалять ветки (локальные/удаленные).
- Выполнять разрушительные операции с рабочим деревом или историей.
- Подключаться по SSH к Raspberry Pi без явного разрешения пользователя.
  Для разрешенного подключения использовать:
  `ssh pi@192.168.0.21` (логин `pi`, пароль `treed`).

## 10) Definition of Done

Задача считается завершенной, когда:
- выполнено ровно то, что запросил пользователь;
- логика/структура/синтаксис проверены;
- даны краткие итоги и ограничения проверки;
- commit/push сделаны только при явном разрешении пользователя.
